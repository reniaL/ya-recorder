# 播放启动进度回跳：真机诊断（2026-10-21）

结论：已在 Android 真机的 debug 版本复现播放器输入位置回退。直接触发因素是 `just_audio 0.10.6` 的位置插值被新的底层位置锚点校正，应用直接将校正结果传给进度条。以下为修复前诊断；后续修复与验证见本文末尾。不记录设备型号、品牌或序列号。

## 方法与结果

临时在 `JustAudioPlaybackBackend` 记录 `play()`、`playbackEventStream` 的 `updatePosition/updateTime` 和 `positionStream` 样本；记录每次播放请求后的前 2200 ms。在设备上通过列表播放按钮操作既有录音，不新增或修改录音内容。结构化证据见 [诊断快照](playback-startup-2026-10-21.json)，原始筛选日志保存在本地 `build/diagnostics/playback-startup-2026-10-21.log`。

两次回退约 189 ms、245 ms。全部新加载样本中，单次回退幅度约 142–245 ms。上述校正前后均为 `playing=true`、`processingState=ready`；原始锚点为 0 → 0 → 9 ms，没有对应的底层锚点后退。

## 原因判断

`just_audio` 的 `_getPositionFor` 在 `playing && ready` 时计算：`updatePosition + (当前时间 - updateTime) × speed`。`play()` 会先立即发布本地播放意图，再异步激活音频会话并发送原生播放请求。因此，`playing && ready` 不足以证明音频时间已持续推进。Android 的新位置事件到达后会更新锚点和时间戳，估算值随之回落；原生 `ObserverRenderer` 也会在检测到位置停留后重新推进时刷新位置事件。

修复前 `AudioPlaybackService._handlePosition` 接受这些样本，`PlaybackProgress` 直接显示 `status.position`。本次日志直接确认了“估算值领先、事件校正后回退”的链路。日志未进一步区分音频会话激活、音轨启动和通道调度各自贡献的耗时，也未采集扬声器波形，不能据此宣称音频样本本身回放或完全没有回放。

## 建议方案

优先保留服务层真实位置，在共享进度显示逻辑中增加连续播放期间的防回退处理：遇到启动校正时暂时保持已显示位置，实际位置追上后继续移动。代价是启动期间可能出现约几百毫秒的短暂停留，应真机比较体验。

必须明确标识主动位置变更边界：切换录音、拖动、快进/快退、停止、完成重播、暂停/恢复等操作重新建立显示基准。尤其不能直接对业务层 `status.position` 全局取最大值，否则会破坏手动回退和后续相对跳转。底部与详情应复用处理逻辑，并验证页面切换后的一致性。

仅等待 `ready`、只屏蔽位置 0、固定延迟若干毫秒或延长进度动画均不能充分解决本次观测到的问题。`play()` 的 Future 通常在播放结束或暂停时完成，也不能将 `await play()` 当作“刚开始发声”的确认。

后续修复应补充位置序列 192 → 3 → 255 → 11 → 正常推进、主动向后 seek、连续快退、切换/返回、短录音重播、倍速及双页面测试，再在真机确认显示与声音的同步体验。

## 修复实现与验证

`AudioPlaybackService` 新增共享的 `displayPosition`。连续处于同一录音的播放状态时，较小的位置校正仍写入真实 `status.position`，显示位置保持，实际进度追上后继续移动。底部播放器与详情的 `PlaybackProgress` 均读取共享显示值，进入详情不会重新从较小的实际值开始显示。

主动 seek、快进/快退与拖动提交均显式重置显示基准。暂停、加载、切换、播放完成、重播、失败和停止等状态转换也会重置。跳转目标仍由真实位置计算；没有修改音频文件、播放速度或底层媒体时钟。
