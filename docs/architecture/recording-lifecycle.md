# 录音生命周期

录音是丫丫录音的核心高风险能力。本文件定义 Android 优先阶段的录音状态、事件和持久化顺序，以避免界面显示已保存但文件不可用，或异常中断时静默丢失已录内容。

## 目标与边界

- 默认输出为 M4A 容器、AAC-LC 编码的单条本地音频文件。
- Flutter 层负责用户界面和业务状态；实际录制、音频焦点、前台服务和系统回调可由 Android 原生层实现。
- 首版一次仅允许一个活跃录音会话。
- 完成保存前的文件不视为用户可管理的录音，不能播放、分享或移动到文件夹。
- 所有会话状态都应能映射为用户可理解的结果，而非仅记录技术错误。

## 状态机

```text
idle
  -> requestingPermission
  -> preparing
  -> recording <-> paused
  -> stopping
  -> saved
  -> idle

recording | paused
  -> discarding
  -> idle

requestingPermission | preparing | recording | paused | stopping
  -> failed
  -> idle
```

### 状态定义

| 状态 | 含义 | 可接受的主要事件 |
| --- | --- | --- |
| `idle` | 没有活动会话。 | 开始录音。 |
| `requestingPermission` | 正在请求或等待麦克风权限结果。 | 已授予、已拒绝、取消。 |
| `preparing` | 正在创建临时文件、配置录音器并启动 Android 前台录音服务。 | 准备完成、准备失败、取消。 |
| `recording` | 正在采集音频。 | 暂停、停止、取消、系统中断。 |
| `paused` | 会话已保留但未采集音频。 | 继续、停止、取消、系统中断。 |
| `stopping` | 已请求停止，正在完成编码器、封装文件和写入索引。 | 保存成功、保存失败。 |
| `saved` | 文件与索引均已可靠提交，可供列表、播放和分享使用。 | 返回空闲状态。 |
| `discarding` | 正在停止录音并删除临时数据。 | 删除完成、删除失败。 |
| `failed` | 当前会话无法继续或无法确认保存结果。 | 展示结果后回到空闲状态。 |

状态转换必须串行执行。界面重复点击停止、暂停或继续时，控制层应忽略无效事件或安全地复用正在进行的操作，不能创建第二个录音器或第二个文件。

## 保存协议

录音文件与索引必须按以下顺序提交：

1. 为会话生成稳定的内部标识，并在应用私有录音目录创建临时路径，例如 `recording-<id>.m4a.part`。
2. 原生录音器向临时文件写入 AAC 音频；会话元数据可作为草稿保存在本地索引中，但不得出现在普通列表。
3. 用户停止或系统要求结束时，调用原生录音器停止并等待其完成 M4A 容器封装。
4. 验证生成文件存在、可读取且具备有效的音频时长或媒体信息。
5. 将临时文件原子地移动或重命名为最终 `.m4a` 文件。
6. 在本地索引中以事务方式提交录音标题、创建时间、时长、文件大小、最终路径和文件夹归属。
7. 仅当文件与索引都成功后才进入 `saved`，并向 Flutter 层发布可显示的录音条目。

若第 3 至第 6 步任一步失败，应用必须保留足以诊断和恢复的状态。它不能创建一个指向不存在文件的普通录音条目。索引写入失败而最终文件存在时，应在下次启动时扫描恢复目录并尝试补建索引。

## 取消与删除临时数据

- 取消只适用于 `preparing`、`recording` 或 `paused` 状态。
- 取消前需获得用户确认，确认后停止原生录音器并删除临时文件与草稿索引。
- 删除失败时，临时文件保留在专用恢复目录中，等待下次启动清理；该文件不对普通列表可见。
- 已经进入 `stopping` 后不允许把停止操作改为取消，避免在文件封装途中破坏已写入的数据。

## Android 运行策略

### 前台与后台

- 录音开始成功后，应使用 Android 前台服务维持录制，并显示系统要求的持续通知。
- 用户切换应用或锁屏后，录音继续还是被系统限制，取决于系统版本、设备策略和权限；应用必须监听原生回调并同步真实状态，不能只依赖 Flutter 页面是否存活。
- Android 进程被系统终止后，不能承诺未完成缓冲区必然可恢复；下次启动应检测遗留临时文件，并向用户提供能恢复的完整录音或清理不可用残留的结果。

### 音频焦点与外部中断

| 事件 | MVP 策略 | 用户可见结果 |
| --- | --- | --- |
| 短暂音频焦点丢失 | 尝试暂停当前会话。 | 显示已暂停，用户可在音频焦点恢复后继续。 |
| 永久音频焦点丢失、来电或麦克风被占用 | 停止采集并执行保存协议。 | 已录部分保存为一条录音，并标记为因系统中断结束。 |
| 麦克风权限被系统撤销 | 停止采集并尝试保存已有内容。 | 提示需要重新授权后才能新建录音。 |
| 存储空间不足或写入错误 | 停止采集并尝试完成当前文件。 | 明确提示保存成功、部分保存或保存失败，不能声称成功而文件不可用。 |

恢复音频焦点不应自动继续录音，必须由用户主动选择继续，避免在用户不知情时重新采集声音。

## 启动恢复

应用启动或从异常结束后恢复时，录音模块应：

1. 检查是否存在未完成会话及临时文件。
2. 对能验证为完整、可播放的文件执行保存协议的剩余步骤，并将其标记为中断结束。
3. 对无法验证的临时文件，不在普通列表中显示；保留足够信息以便安全清理，并在适当的产品设计中向用户说明结果。
4. 修复索引与文件系统的不一致：移除指向不存在文件的索引，或为存在的最终文件补建索引。

## Flutter 与原生层契约

Flutter 业务层不直接推断录音结果，而是订阅录音服务发出的事实事件。初始接口至少需要表达：

- 命令：请求权限、开始、暂停、继续、停止、取消。
- 状态：当前生命周期状态、已录时长、是否可继续、当前会话标识。
- 结果：已保存录音的内部标识与路径、失败原因、是否由系统中断结束。
- 事件：权限变化、音频焦点变化、服务意外停止、存储错误和保存完成。

原生层必须将重复事件、生命周期竞态和后台回调收敛后再通知 Flutter。Flutter 只根据该契约更新界面、索引和用户反馈。

## 必测场景

在开始实现录音模块前，应为以下场景准备真机验证用例：

1. 录音、暂停、继续、停止后的文件可播放，时长正确。
2. 连续快速点击暂停、继续和停止不会造成崩溃、重复文件或卡在中间状态。
3. 锁屏、切后台和从最近任务返回后，录音状态与实际文件一致。
4. 来电、闹钟、其他应用播放音频、蓝牙耳机连接或断开后的结果符合中断策略。
5. 磁盘空间不足、麦克风权限拒绝或撤销、文件写入失败时，没有虚假的成功条目。
6. 录音中强制结束应用后重启，应用能安全处理遗留文件与索引。
