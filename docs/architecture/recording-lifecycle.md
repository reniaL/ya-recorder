# 录音生命周期

录音是丫丫录音的核心高风险能力。本文件定义 Android 优先阶段的录音状态、事件和持久化顺序，以避免界面显示已保存但文件不可用，或异常中断时静默丢失已录内容。

## 目标与边界

- 支持 MP3 与 M4A 两种输出格式；初始默认 M4A（AAC-LC），用户可在设置中持久化默认格式。
- 开始录音时读取偏好并固定本次会话格式；后续设置变更仅影响下一次录音，已有录音不转换。
- Flutter 层负责用户界面和业务状态；实际录制、音频焦点、前台服务和系统回调可由 Android 原生层实现。
- 首版一次仅允许一个活跃录音会话。
- 主要面向几分钟录音，当前验收取样为 1–5 分钟及极短录音边界；一小时压力测试暂缓，不作为当前验收关口，也不据此新增录音时长上限。测试范围以 [产品基线](../product/feature-list.md#产品目标)为准。
- 完成保存前的文件不视为用户可管理的录音，不能播放、分享或移动到文件夹。
- 所有会话状态都应能映射为用户可理解的结果，而非仅记录技术错误。

## 录音格式方案（2026-10-07）

REC-07 采用 MP3 实时编码方案，保留现有 M4A 实现。独立原型、统一格式契约、旧索引迁移、后端接口及正式 MP3 后端代码已实现；MP3 暂时只在显式开启的 debug 构建中可调用，普通构建和主界面仍录制 M4A。原型设备关口、正式参数、设置/分享和保存/恢复接入待完成。下文的完整编码与恢复策略是目标设计，不能据此视为已经实现。

### Android 编码路径

| 格式 | 采集与编码路径 | 停止后的工作 |
| --- | --- | --- |
| M4A | 沿用 `MediaRecorder`，采集并编码 AAC-LC，写入 M4A 临时文件。 | 停止录音器并完成容器封装，验证后提交文件与索引。 |
| MP3 | `AudioRecord` 采集 PCM，经有容量限制的队列交给编码线程，使用 LAME 输出 MP3 临时文件。 | 停止接收新样本，排空已接收队列，flush 编码器，补齐必要的文件信息并关闭，验证后提交文件与索引。 |

MP3 不采用“先录 M4A，停止后转换”的路径，也不将完整 PCM/WAV 作为常规中间文件落盘。这样避免 AAC 到 MP3 的二次有损编码、整段转码等待和双份完整文件占用；代价是需要自行维护采集、缓冲、编码线程及其异常行为。编码性能、耗电和停止等待须在目标设备实测，不据此承诺固定保存耗时或绝对的省电优势。

Android 原生层为两种录音实现提供统一的开始、暂停、继续、停止、取消及资源释放接口，复用前台服务、状态机、保存协议和事件桥接。Flutter 不直接处理 PCM 或调用编码器。M4A 路径保持现有参数；MP3 正式参数在开放产品入口前通过真实短语音试听及 1–5 分钟真机原型确定，第四步暂用原型候选值并保留 debug 开关。首版不提供用户可调的高级参数。

LAME 为编码核心的选型方向；具体 Android 封装、版本及构建方式仍需验证维护状态、许可、目标 ABI 与 16 KB 内存页兼容性，不直接照搬旧示例的依赖配置。MP3 编码器初始化失败应明确报错，不静默改用 M4A，也不修改用户偏好。

### 实时采集与会话控制

- 采集线程及时读取 `AudioRecord`，编码与磁盘写入不阻塞采集；队列必须有容量上限，避免采集期间内存持续增长。队列持续积压或写入/编码失败时，停止接收新样本，尽力保存可验证的已录部分并反馈实际结果，不能静默丢帧后报告完整保存。
- 暂停命令与采集串行协调，确定暂停边界后不再接收暂停期间的样本；已接收样本可继续编码。保留同一编码器、临时文件和会话，不在暂停时执行最终 flush，也不将多个独立 MP3 文件拼接作为继续方案。
- 继续时重新接收样本并送入同一编码器。时长以实际接受的音频样本为依据，排除暂停时间；保存时验证媒体时长，并考虑编码延迟及尾部填充信息。
- 停止时确定最后接收样本的边界，再排空队列与编码器缓冲，关闭文件；收尾失败保留可诊断与恢复的临时数据。`stopping` 期间维持必要的服务生命周期，直到收尾与保存结果处理完成。
- 取消需用户确认；确认后协调停止采集和编码线程，释放资源后删除临时文件及草稿，不生成普通录音索引。重复或并发命令不能导致重复 flush、重复保存或文件关闭后继续写入。

### 格式、元数据与兼容

- 使用统一格式定义映射扩展名与 MIME 类型：M4A 为 `.m4a` / `audio/mp4`，MP3 为 `.mp3` / `audio/mpeg`。恢复目录、最终路径及分享副本均由本次录音格式确定。
- 会话草稿与录音索引记录格式；为旧索引补充格式时，以旧版本仅产生 M4A 为迁移依据，保留文件、路径、标题、时长与文件夹归属，升级不重新编码。
- 播放和分享使用录音自身的格式与实际路径，不读取当前默认偏好推断旧文件格式。混合格式列表继续支持搜索、重命名、移动、删除和恢复。

### 已实现的格式契约（REC-07 第二步）

以下记录第二步的实现边界；第四步在 debug 开关开启时允许 MP3，普通构建仍保留拒绝路径。

- Dart 与 Kotlin 的 `RecordingFormat` 使用稳定协议值 `m4a`、`mp3`，统一扩展名与 MIME 映射。开始命令显式传入 `format`；原生 `ActiveSession` 固定格式，状态与保存结果回传同一字段。无会话的 `idle` / `failed` 可为空，其余状态或带会话 ID 的状态必须带有效格式。
- 缺失或未知的格式值拒绝解析，不推断为 M4A。原生桥接在启动服务前拒绝未知值（`recording-format-invalid`）及尚未接入编码器的 MP3（`recording-format-unavailable`），不修改已运行会话；服务入口也校验格式。主界面本阶段明确请求 M4A。
- 完成与临时路径按显式格式生成，分别为 `recording-<id>.<format>` 与 `recording-<id>.<format>.part`。保存事件及索引写入要求最终扩展名与格式一致，拒绝将临时文件或错误扩展名作为保存结果。
- SQLite 版本 3 为 `recordings` 新增非空 `format` 列，仅允许 `m4a` / `mp3`。版本 1、2 的旧记录依据历史仅产生 M4A 的事实补为 `m4a`；版本 1 同时沿用既有文件夹排序迁移。升级使用数据库事务，失败回滚，保留所有既有元数据、文件夹顺序和音频文件；不转码或改动路径。
- 索引已支持混合格式的保存、重命名、移动、软删除、恢复及重启读取。现有播放器继续使用记录的文件路径；本阶段分享服务明确拒绝 MP3，避免沿用 M4A 分享接口错误标注 MIME，正式 MP3 分享适配待后续步骤。

这些检查保证格式在各层显式传递，不替代媒体完整性验证、跨文件与数据库的保存协议、草稿恢复或 MP3 真机验收。

### 已实现的原生后端接口（REC-07 第三步）

以下记录第三步提交时的边界；第四步增加 MP3 后端、样本计时、异步错误回传和服务工作线程。

- `RecordingBackend` 为单次会话提供 `prepare`、`start`、`pause`、`resume`、`stop`、`cancel`、`release` 及固定 `format`。`RecordingService` 串行调用后端，继续负责状态机、暂停排除计时、前台通知、媒体时长读取、临时文件提交和事件发布；Flutter 与 SQLite 契约不变。
- `RecordingBackendFactory` 按会话格式创建后端，本阶段只创建 `M4aRecordingBackend`，MP3 仍明确拒绝，不创建或回退到 M4A。准备与开始分离，保持先完成录音器准备、再进入前台服务、最后开始采集的顺序。
- M4A 后端通过 `AndroidM4aRecorder` 沿用 `MediaRecorder` 的 MIC / MPEG-4 / AAC、128 kbps、44.1 kHz 配置；不新增声道设置。暂停与继续复用同一个实例和临时文件；计时仍使用服务的单调时钟，保存时长仍读取媒体信息。
- `stop` 完成录音器收尾并释放资源后返回，失败向服务传播并保留临时文件。`cancel` 容忍短录音的原生停止异常，随后释放资源；后端不删除或移动音频，服务完成取消清理。`release` 不尝试保存，支持重复调用，并在 `reset` 失败时仍尝试原生释放。
- 开始、暂停、继续、保存失败及服务销毁统一释放后端，避免错误后还持有录音器；释放异常不覆盖原始操作错误。取消的非短录音清理异常以 `recording-cancel-failed` 反馈，保留临时文件供后续恢复设计处理。
- 当前后端命令同步执行，延续现有 M4A 调用方式。MP3 的采集/编码线程、异步错误回传、样本计时及停止排空调度需在后续接入时实现，不能将长时间排空放到服务主线程。

原生测试通过可注入录音器覆盖会话复用、操作顺序、重复收尾、准备/开始/停止失败、短录音取消、失败清理与文件职责；这些测试不运行 Android 麦克风或验证实际 AAC 音频，M4A 真机回归仍待完成。

### MP3 后端接入（REC-07 第四步）

已接入 `AudioRecord → 有界 PCM 队列 → LAME` 实时后端，暂停/继续复用编码器，正常停止排空并 flush/回填标签/fsync，取消跳过最终 flush。MP3 状态时长由接受样本计算；服务命令、错误和收尾串行运行在工作线程，避免主线程等待编码排空。编码核心抽为正式应用与原型共用的 `android/mp3-encoder`，APK 附带对应源码与构建材料。

当前仅 `rec07Mp3=true` 的 debug 开放原生 MP3 命令，所有 release 与普通 debug 仍关闭，主界面仍明确请求 M4A；设置/分享尚未接入。正式应用 37 项 JVM 测试、桌面正式 Kotlin/JNI 暂停/继续流的 220,560 样本完整解码、共享模块 lint、APK 构建及 16 KB 静态对齐通过。Android 设备关口未通过，错误后部分保存、草稿与恢复仍待第五步及 REC-06；完整边界与复现方式见 [MP3 后端记录](mp3-backend.md)。

### 方案依据

- [axet Audio Recorder 采集源码](https://gitlab.com/axet/android-audio-recorder/-/blob/master/app/src/main/java/com/github/axet/audiorecorder/app/RecordingStorage.java)同时提供实时编码和原始 PCM 暂存路径；[MP3 编码源码](https://gitlab.com/axet/android-audio-library/-/blob/master/src/main/java/com/github/axet/audiolibrary/encoders/FormatMP3.java)使用 LAME。
- [TAndroidLame 录音示例](https://github.com/naman14/TAndroidLame/blob/master/app/src/main/java/com/naman14/tandroidlame/Mp3AudioRecordActivity.java)展示 `AudioRecord → PCM → LAME → MP3` 的实时路径；仅作为实现参考，不代表已满足本项目的后台、并发或异常保护要求。
- [Android 格式支持说明](https://developer.android.com/media/platform/supported-formats)不保证内置 MP3 编码器；[AudioRecord 接口说明](https://developer.android.com/reference/android/media/AudioRecord)要求应用及时读取采集缓冲。

## 状态机

```text
idle
  -> requestingPermission
  -> preparing
  -> recording <-> paused
  -> stopping
  -> saved
  -> idle

recording | paused
  -> discarding
  -> idle

requestingPermission | preparing | recording | paused | stopping
  -> failed
  -> idle
```

### 状态定义

| 状态 | 含义 | 可接受的主要事件 |
| --- | --- | --- |
| `idle` | 没有活动会话。 | 开始录音。 |
| `requestingPermission` | 正在请求或等待麦克风权限结果。 | 已授予、已拒绝、取消。 |
| `preparing` | 已固定本次格式，正在创建临时文件、配置对应采集/编码器并启动 Android 前台录音服务。 | 准备完成、准备失败、取消。 |
| `recording` | 正在采集音频。 | 暂停、停止、取消、系统中断。 |
| `paused` | 会话已保留但未采集音频。 | 继续、停止、取消、系统中断。 |
| `stopping` | 已请求停止，正在处理剩余样本与编码缓冲、完成文件收尾和写入索引；不对整段录音执行格式转换。 | 保存成功、保存失败。 |
| `saved` | 文件与索引均已可靠提交，可供列表、播放和分享使用。 | 返回空闲状态。 |
| `discarding` | 正在停止录音并删除临时数据。 | 删除完成、删除失败。 |
| `failed` | 当前会话无法继续或无法确认保存结果。 | 展示结果后回到空闲状态。 |

状态转换必须串行执行。界面重复点击停止、暂停或继续时，控制层应忽略无效事件或安全地复用正在进行的操作，不能创建第二个录音器或第二个文件。

## 保存协议

录音文件与索引必须按以下顺序提交：

1. 为会话生成稳定的内部标识，固定格式，并在应用私有恢复目录创建对应的临时路径，例如 `recording-<id>.m4a.part` 或 `recording-<id>.mp3.part`；持久化足够的会话信息以支持异常恢复。
2. 对应录音实现向临时文件持续写入 AAC/M4A 或 MP3 音频；会话元数据作为草稿保存，不得出现在普通列表。
3. 用户停止或系统要求结束时，停止采集并等待收尾。M4A 完成原生容器封装；MP3 排空已接收样本、flush 编码器并写入必要的文件信息，不重新编码整段录音。
4. 验证生成文件存在、可读取且具备有效的音频时长或媒体信息。
5. 将临时文件原子地移动或重命名为最终 `.m4a` 或 `.mp3` 文件。
6. 在本地索引中以事务方式提交录音标题、创建时间、时长、文件大小、格式、最终路径和文件夹归属。
7. 仅当文件与索引都成功后才进入 `saved`，并向 Flutter 层发布可显示的录音条目。

若第 3 至第 6 步任一步失败，应用必须保留足以诊断和恢复的状态。它不能创建一个指向不存在文件的普通录音条目。索引写入失败而最终文件存在时，应在下次启动时结合会话草稿、恢复目录与最终录音目录尝试补建索引。

## 取消与删除临时数据

- 取消只适用于 `preparing`、`recording` 或 `paused` 状态。
- 取消前需获得用户确认，确认后停止原生录音器并删除临时文件与草稿索引。
- 删除失败时，临时文件保留在专用恢复目录中，等待下次启动清理；该文件不对普通列表可见。
- 已经进入 `stopping` 后不允许把停止操作改为取消，避免在文件封装途中破坏已写入的数据。

## Android 运行策略

### 前台与后台

- 录音开始成功后，应使用 Android 前台服务维持录制，并显示系统要求的持续通知。
- 用户切换应用或锁屏后，录音继续还是被系统限制，取决于系统版本、设备策略和权限；应用必须监听原生回调并同步真实状态，不能只依赖 Flutter 页面是否存活。
- Android 进程被系统终止后，不能承诺未完成缓冲区必然可恢复；下次启动应检测遗留临时文件，并向用户提供能恢复的完整录音或清理不可用残留的结果。

### 音频焦点与外部中断

| 事件 | MVP 策略 | 用户可见结果 |
| --- | --- | --- |
| 短暂音频焦点丢失 | 尝试暂停当前会话。 | 显示已暂停，用户可在音频焦点恢复后继续。 |
| 永久音频焦点丢失、来电或麦克风被占用 | 停止采集并执行保存协议。 | 已录部分保存为一条录音，并标记为因系统中断结束。 |
| 麦克风权限被系统撤销 | 停止采集并尝试保存已有内容。 | 提示需要重新授权后才能新建录音。 |
| 存储空间不足或写入错误 | 停止采集并尝试完成当前文件。 | 明确提示保存成功、部分保存或保存失败，不能声称成功而文件不可用。 |

恢复音频焦点不应自动继续录音，必须由用户主动选择继续，避免在用户不知情时重新采集声音。

## 启动恢复

应用启动或从异常结束后恢复时，录音模块应：

1. 检查是否存在未完成会话及两种格式的临时文件，按持久化的会话格式选择验证路径；取消残留与待恢复会话须能区分。
2. 对能验证为完整、可播放的文件执行保存协议的剩余步骤，并将其标记为中断结束。
3. 对无法验证的临时文件，不在普通列表中显示；保留足够信息以便安全清理，并在适当的产品设计中向用户说明结果。
4. 修复索引与文件系统的不一致：移除指向不存在文件的索引，或为存在的最终文件补建索引。

MP3 异常结束可能留下完整帧和不完整尾部，恢复必须验证实际可解码范围及媒体时长；只将验证通过的内容提交为中断录音，必要时丢弃损坏尾部并说明恢复结果。没有独立源文件可重编码，不承诺恢复所有样本或未写入的缓冲。M4A 仍需验证容器是否完整，不因 MP3 增加而降低原有恢复要求。

## Flutter 与原生层契约

Flutter 业务层不直接推断录音结果，而是订阅录音服务发出的事实事件。初始接口至少需要表达：

- 命令：请求权限、开始（携带已读取的格式）、暂停、继续、停止、取消；原生层校验格式，不接受不支持的值。
- 状态：当前生命周期状态、已录时长、是否可继续、当前会话标识及会话格式。
- 结果：已保存录音的内部标识、路径与格式、失败原因、是否由系统中断结束。
- 事件：权限变化、音频焦点变化、服务意外停止、存储错误和保存完成。

原生层必须将重复事件、生命周期竞态和后台回调收敛后再通知 Flutter。Flutter 只根据该契约更新界面、索引和用户反馈。

## 必测场景

在开始实现录音模块前，应为以下场景准备真机验证用例：

1. 分别选择 MP3、M4A，录音、暂停、继续、停止后的文件可播放，时长正确；MP3 暂停期间无额外静音，续录保持同一文件。
2. 连续快速点击暂停、继续和停止不会造成崩溃、重复文件或卡在中间状态。
3. 锁屏、切后台和从最近任务返回后，录音状态与实际文件一致。
4. 来电、闹钟、其他应用播放音频、蓝牙耳机连接或断开后的结果符合中断策略。
5. 磁盘空间不足、麦克风权限拒绝或撤销、文件写入失败时，没有虚假的成功条目。
6. 录音中强制结束应用后重启，应用能安全处理遗留文件与索引。
7. 格式设置即时保存、重启保持、修改后从下次会话生效；升级保留旧 M4A 数据，混合格式的播放、进度、倍速、分享 MIME/附件名、删除和恢复正常。
8. 两种格式分别验证 1–5 分钟代表性录音，MP3 检查音频连续性、时长、内存/队列是否持续积压及停止收尾耗时；另用约 10 秒语音比较 MP3 参数，并覆盖立即停止/取消、极短尾块等边界。锁屏、切后台和返回可合并在这段几分钟录音中执行；记录设备、参数及结果，验收不以桌面编译代替真机证据。一小时录音与长期 CPU/耗电趋势测试暂缓。
9. 编码器不可用、采集错误、队列满、编码/写入错误、收尾失败及索引提交失败，均有准确反馈与可诊断残留，无静默格式切换、虚假完整保存或重复索引；验证两种格式的锁屏/后台行为及 MP3 原生库兼容性。
