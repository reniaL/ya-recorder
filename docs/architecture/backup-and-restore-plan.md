# 备份与恢复方案参考

整理日期：2026-10-14。

本文汇总关于丫丫录音数据可靠性的讨论，供后续产品设计和开发参考。内容属于方案建议，不代表功能已经实现或正式纳入 MVP；具体范围、交互和验收标准需在立项时确认。外部服务信息沿用本次讨论中的公开资料，正式接入前应重新核对接口与授权条件。

2026-10-15 已确认第一版手动 ZIP 备份与恢复方案，详见 [第一版设计](manual-backup-and-restore-design.md)及 [七步实现计划](manual-backup-and-restore-implementation-plan.md)。范围已登记至产品和进度，第一步协议基础已实现，完整导入导出尚未实现。本文保留路线比较及后续建议；第一版的数据范围、加密和冲突处理以该设计为准。

## 1. 当前存储结构与风险

应用的录音、文件夹和索引保存在设备本地，不要求账户登录。Android 主用户下，应用私有目录通常为：

```text
/data/user/0/io.github.renial.ya_recorder/files/ya_recorder/
├── recordings/   已完成的录音
├── recovery/     录音草稿及恢复相关文件
└── index.db      SQLite 索引与偏好数据
```

录音文件以稳定 ID 命名，如 `recording-<ID>.aac`、`recording-<ID>.mp3` 或旧格式 `.m4a`。实际应用目录由系统分配，上述路径不应硬编码。文件夹是索引中的逻辑分类，不对应独立音频目录。

代码依据：

- [本地路径定义](../../lib/storage/app_storage_paths.dart)
- [Android 录音服务](../../android/app/src/main/kotlin/io/github/renial/ya_recorder/RecordingService.kt)
- [录音索引模型](../../lib/storage/models/recording.dart)

手机丢失、损坏、卸载应用或清除应用数据，均可能造成录音及索引丢失。已有的中断录音恢复能力针对录音生命周期异常，不能替代手机之外的数据备份。

可靠性目标是：至少有一份包含音频和必要元数据、可在新手机上恢复的副本，保存在手机之外。复制到同一部手机的其他目录，只能覆盖部分误删或卸载场景，不能覆盖整机丢失、损坏。

## 2. 常见方案比较

成本为针对当前项目的相对评估，包含开发、验证及长期维护，不是工期承诺。

| 方案 | 实现成本 | 用户体验 | 安全与可靠性 | 建议 |
| --- | --- | --- | --- | --- |
| 手动导出完整备份包，保存到电脑、外置存储或网盘 | 低—中 | 操作直观，但容易忘记 | 用户掌握副本；恢复范围取决于上次备份时间 | 第一阶段优先 |
| 定期备份到指定目录，由其他工具上传 | 中 | 配置后较省心，依赖外部工具 | 应用通常只能确认本地写入，不能确认远端上传完成 | 轻量自动化候选 |
| 直接备份到用户自己的网盘、WebDAV 或 NAS | 中—高 | 初次配置稍复杂，之后可自动运行 | 用户选择服务；需处理授权、加密和失败重试 | 第二阶段推荐 |
| 自建云端账户与备份服务 | 高，持续运营成本高 | 登录后使用较简单 | 开发方承担账户恢复、访问控制、存储和可用性责任 | 用户规模扩大后评估 |
| Android 系统自动备份 | 配置低，验证中 | 通常无需操作，过程不透明 | 受容量、设备、账户和系统策略限制 | 补充手段 |
| 多设备双向同步 | 很高 | 多台设备使用方便 | 删除和损坏可能传播；仍需历史备份 | 后续独立评估 |

备份与同步应区分：备份保留可恢复的历史状态；同步传播当前状态。仅保留最新云端状态，可能在本地误删后同步删除副本。多设备同步需要额外处理重命名、移动、删除、并发修改和冲突，不宜作为当前可靠性需求的第一步。

## 3. 推荐实施顺序

1. **完整备份包与恢复**：先打通换机恢复链路，支持音频与元数据，并设计加密能力。
2. **备份提醒与状态**：显示上次导出时间、此后新增录音数量，提示将副本保存到手机之外。
3. **可选自动异地备份**：先评估一种通用接口，例如 WebDAV；支持增量上传、失败重试和历史版本。
4. **按实际需求评估自建云服务与多设备同步**：分别确认持续运营成本和冲突处理成本。

本地录音保存始终优先，备份失败不应阻止录音。云端功能由用户主动启用，离线录音与播放继续可用。

## 4. 第一阶段：手动导出与导入

### 4.1 备份内容

单个录音的分享不等于完整备份。建议备份包包含：

- 全部已完成音频，保留原格式，不重新编码。
- 录音元数据：ID、标题、创建时间、格式、时长、大小、文件夹 ID、删除时间和中断标记。
- 文件夹元数据：ID、名称、排序等必要字段。
- 可选应用偏好，恢复时允许用户决定是否导入。
- 备份格式版本、创建时间、文件清单、相对路径和校验值。

建议包含保留期内的最近删除录音，并保留其状态。需明确恢复后沿用原删除时间还是重新计算保留期，避免导入后立即被清理而用户不知情。正在录制的文件及未完成草稿不混入普通已完成备份；草稿恢复属于另一个需要明确设计的场景。

可采用容器文件存放音频与版本化 JSON 元数据。普通 ZIP 适合未加密容器；敏感备份应使用成熟的认证加密方案，不能把弱 ZIP 密码保护当作充分的安全保障。具体扩展名、容器和加密库在实施时确定。

### 4.2 导出步骤

1. 用户进入“备份与恢复”，选择“导出备份”。
2. 应用展示录音数量、预计大小、最近删除包含规则，并提供加密选项。
3. 用户通过系统文件选择器选择保存位置，或选择生成后分享给其他应用。
4. 应用获取一致的元数据快照并保护对应音频，生成文件清单和校验值；大文件采用流式处理，避免整体读入内存。
5. 完成写入后检查备份结构及完整性；失败或取消时不把半成品标记为成功。
6. 展示文件名和保存位置，记录上次成功导出时间；提示将文件复制到电脑、外置存储或上传网盘。

最基础的目标是手机“下载”或“文档”目录。系统文件选择器也可能提供连接的 U 盘或已安装的网盘服务，取决于设备和服务是否支持 Android 文档接口。不能预先保证某个网盘一定会出现在选择器中。[Android 文件访问文档](https://developer.android.com/training/data-storage/shared/documents-files)

### 4.3 导入步骤

1. 用户把备份包下载或复制到新手机；若文档服务支持，也可通过选择器直接读取。
2. 在应用中选择“从备份恢复”，选取文件；加密备份输入密码或恢复密钥。
3. 应用检查格式版本、必要字段、文件清单及校验值，展示备份时间、数量和异常。
4. 用户确认导入；默认合并保留当前数据，覆盖恢复作为单独操作。
5. 应用将音频写入当前设备的私有目录，重建索引中的本地路径，再提交恢复结果。
6. 展示导入、跳过及失败数量，并可查看具体原因；确认录音可播放、标题和文件夹关系正确。

合并时以稳定 ID 去重，同时核对内容和元数据；相同 ID 但内容不同应作为冲突处理，不能静默覆盖。文件夹 ID 冲突需同步调整归属关系。恢复过程中失败应保留原有数据，使用临时文件和数据库事务设计可回滚的提交过程。

### 4.4 一致性与兼容性

当前索引的 `file_path` 是绝对路径。换手机后不能直接复用，应在备份中使用相对路径或 ID，恢复时生成新的绝对路径。

不建议简单复制正在使用的 `index.db`。SQLite 的事务及可能存在的 WAL 文件需要一致快照；推荐第一版导出版本化 JSON，恢复时重建数据库。直接备份数据库也可行，但必须使用正确的快照方式，并处理数据库版本迁移。

导出期间发生新录音入库、删除或重命名时，要保证清单与音频属于一致状态。可对必要操作进行短暂协调，并防止快照中的文件被并发清理；具体机制需结合现有保存、最近删除和永久删除逻辑设计。

导入文件属于外部输入，需要限制解压大小与条目数、拒绝越界路径、验证支持的格式，并在写入前检查空间。旧版本备份要有迁移策略；未来版本无法识别的备份应明确提示，不能部分静默恢复。

### 4.5 用户可见状态

| 实际结果 | 建议表达 |
| --- | --- |
| 文件成功写入手机目录 | 已导出到手机；请将备份保存到手机之外 |
| 文件交给其他应用处理 | 已交给目标应用，请在该应用确认上传结果 |
| 直接连接远端，上传且校验完成 | 异地备份完成，并显示完成时间 |
| 用户取消或写入失败 | 未完成备份，说明原因并保留重试入口 |

“上次导出时间”和“上次确认的远端备份时间”是不同信息，不能混用。备份之后新增或修改的数据仍可能未被保护。

## 5. 加密与恢复密钥

建议对第三方存储上的备份提供客户端加密，音频与标题等元数据一起保护。传输连接也应使用 HTTPS。

密钥恢复机制必须能在原手机丢失后使用，可选备份密码或用户独立保存的恢复密钥。首次配置时引导用户保存并确认；忘记密码或丢失恢复密钥，可能无法解密，开发者也无法代为恢复。

Android Keystore 适合保护本机凭据，其密钥不可直接导出。因此异地备份不能仅依赖原手机的 Keystore 密钥，必须另有可在新设备恢复解密能力的设计。[Android Keystore 文档](https://developer.android.com/privacy-and-security/keystore)

采用成熟库与密码派生机制，避免自创加密协议。验收时不仅验证原手机能解密，还要验证无原设备密钥的新手机能够恢复。

## 6. 第二阶段：自动异地备份

### 6.1 用户自有服务

优先评估 WebDAV 等通用接口，例如 Nextcloud 的 WebDAV 文件访问能力。首次配置需要地址、授权信息和目标目录，使用成本高于直接登录产品自有账户，但无需先建设完整账户体系。[Nextcloud 官方文档](https://docs.nextcloud.com/server/latest/user_manual/en/files/access_webdav.html)

NAS 是手机外的副本，但家中 NAS 与手机仍可能受到同一场灾害或盗窃影响；重要数据可再保留其他地点的副本。

### 6.2 上传与恢复机制

- 本地录音完成保存后进入备份队列；只处理已完成内容。
- 音频按 ID 或内容校验值增量上传，元数据保留版本快照，避免每次全量重传。
- 支持网络条件、失败重试和中断后继续；授权失效时提示重新授权。
- 音频上传并确认完整后，再发布对应快照清单。恢复时只接受完整快照。
- 保留多个历史恢复点，本地删除不立即清除历史备份；提供明确保留期和远端删除入口。
- 显示待备份数量、最近成功时间、失败原因和“立即重试”。

Android WorkManager 支持持久化任务、运行条件和重试，可作为后台调度候选。具体执行时间受系统调度影响，不能承诺录音结束后立即上传成功。[Android 后台任务文档](https://developer.android.com/develop/background-work/background-tasks/persistent)

如果采用“导出目录＋外部工具上传”，没有远端确认机制时只能报告本地副本生成成功。

## 7. Android 系统备份作为补充

Android Auto Backup 云端备份每个应用的上限为 25 MB，录音积累后容易超过，并受设备、账户、备份服务和系统策略影响，不能作为录音库唯一保障。[Android Auto Backup 文档](https://developer.android.com/identity/data/autobackup)

当前项目主 Manifest 未显式配置 `allowBackup` 或备份排除规则。应用业务完全离线，不代表操作系统一定不会备份其数据；应检查最终合并 Manifest，并制定明确策略。

需避免仅恢复索引而没有对应音频，产生无法播放的条目。系统备份可作为偏好设置或经过验证的换机迁移补充，但音频与索引的恢复一致性仍需单独验证。

## 8. 后续实施步骤与验收

正式实施前依次完成：

1. 确认备份范围、最近删除规则、加密要求、默认合并及冲突策略。
2. 定义版本化备份格式、元数据字段、路径规则、校验与迁移机制。
3. 实现一致快照导出、系统文件保存和通用分享入口。
4. 实现导入预览、完整性验证、路径重建、合并和失败回滚。
5. 增加导出状态、备份提醒及新手机恢复指引。
6. 按正式范围更新功能列表、用户流程、交互设计和开发进度，再实施及验证。
7. 基础恢复链路稳定后，独立评估 WebDAV 等远端接入。

核心验收：**在一台没有原应用数据的新手机上，能够从备份恢复录音、标题和文件夹，并正常播放。** 上传成功只是其中一步。

建议覆盖以下场景：

- AAC、MP3、旧 M4A、中文和长标题、空文件夹、最近删除录音及应用偏好。
- 加密备份的新设备解密、错误密码、损坏文件、缺失音频和不支持版本。
- 重复导入、同 ID 内容冲突、文件夹冲突，确认当前数据不被静默覆盖。
- 空间不足、取消操作、进程终止、写入或分享失败，确认原数据保持可用。
- 导出期间录音入库、重命名、移动、删除及过期清理的一致性。
- 自动备份阶段的断网重试、授权失效、不完整上传和历史快照恢复。
