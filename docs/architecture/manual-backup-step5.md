实现日期：2026-10-15。状态：合并引擎、SQLite 原子提交和启动清理已交付，自动化通过；实际 Android 文档服务、进程终止及重启待设备验收，保留“进行中”。对应 [七步计划](manual-backup-and-restore-implementation-plan.md)第五步。正式设置入口、页面和结果展示留在 BKP-06。

## 执行路径与整包验证

[BackupImportService](../../lib/backup/backup_import_service.dart) 绑定与录音相同的协调器，复用文档选择、真实录音空闲检查、单任务租约和业务写入门禁。选择器取消不取得门禁；预检查、确认等待、文件就位、事务和正常清理期间持续保护业务数据。

原生 `dataSync` 工作线程先流式暂存源 URI，再由 [BackupZipImporter](../../android/app/src/main/kotlin/io/github/renial/ya_recorder/BackupZipImporter.kt) 检查 ZIP。构造 `ZipFile` 前，以有界随机读取预检原始中央目录：最多 10,002 条、目录最多 4 MiB、文件名最多 180 字节、JSON 各 16 MiB、音频总量沿用协议 16 GiB。拒绝多盘、加密、非 STORE、目录/Unix 非普通文件、重复名称、非法路径、局部头名称或方法/标志不一致，以及超过目录边界的内容。原始条目不会在查重之前被按名称去重。

**当前导入明确拒绝 ZIP64，包括其目录哨兵和中央目录附加字段；源 ZIP 必须小于 `0xffffffff` 字节。** 不截断 64 位偏移，不把超过实现能力的包当作成功。导出端仍可产生 ZIP64，因此大容量导出包的跨设备恢复尚不能验收；解除这一限制和实际超过 4 GiB 的验证继续列为发布前缺口。协议的 16 GiB 资源上限不代表本轮导入已支持这一容量。

通过结构检查后，将全部条目流式写入任务私有暂存目录，计算大小、CRC 和 SHA-256，包含之后会因 ID 重复而跳过的音频。条目路径只用于白名单校验，磁盘暂存使用已验证的 basename，不按外部路径任意解压。临时验证报告保留两份有界 JSON 和真实计算的哈希；Dart 独立 isolate 用第一步 `BackupContract` 重新验证版本、字段、ID、引用、条目清单、metadata 和每份音频哈希，全部通过后才生成预览。

预检查只写任务暂存，不修改录音索引或文件夹。原生检查阶段结束即停止服务，等待确认不维持无限前台任务；确认通过桥接要求应用处于前台，再启动文件复制阶段。取消等待会唤醒确认 Future；页面如何返回和重新进入由第六步接入。修复了前一阶段完成快照早于服务停止、下一阶段可能被旧服务 `stopSelf` 影响的竞态，并在服务结束时清除旧阶段超时回调。

## 合并与文件夹规则

- 用包括最近删除在内的所有本地录音 ID 查重。同 ID 不覆盖、不修复，也不自动恢复最近删除；不同 ID 正常导入。
- 对同 ID 的本地音频检查普通文件、索引大小和可读性，并在独立 isolate 计算哈希；缺失或不一致明确失败。音频或标题、时间、时长、格式、归属、中断标记不同只计为差异跳过；完全一致计为重复跳过。
- 同 ID 文件夹保留本地名称和排序；新 ID 按备份 `sort_order, id` 顺序追加在本地最大排序值之后。同名依照 SQLite ASCII NOCASE 规则尝试 `名称（导入）`、`名称（导入 2）`，直到唯一。保留所有空文件夹。
- 新音频保留原 ID/格式，最终路径使用 `recordings/import-<任务 UUID>/recording-<录音 ID>.<格式>`，索引记录当前设备的绝对路径。专属目录与普通录音目录并存，播放器、导出、分享和删除继续使用索引路径。
- 若常规规范目标路径已经有无索引文件，或本任务专属目录已被占用，则拒绝；原生创建目标文件也要求原先不存在，不覆盖已有内容。无新增录音但有空文件夹可以成功；完全重复返回无新增结果。

暂存 ZIP、完整解出内容和新录音最终副本可能同时占用空间。原生在解出前检查当前可用空间能容纳全部条目，文件就位前检查待新增副本；未知源长度分块读取并施加源包上限，磁盘不足/读写失败由实际 IO 报告。不会把一个音频大小数字当作整个流程的精确空间需求。

## 提交协议与恢复权威

SQLite **v8** 仅增加 `backup_import_commits(task_id, committed_at)`；既有 v7 及更早升级路径保留，不重建 ID、音频、文件夹或设置。

1. 确认后，先将 UUID、版本和最终文件 basename 清单写入私有 `backup-imports/<UUID>.json.pending`，flush 后重命名为正式 journal。
2. journal 存在之后才创建本任务专属最终目录，并在原生工作线程逐个复制新音频、fsync。取消在原生块边界处理，不让 Flutter 持有音频字节数组。
3. 全部文件就位后再次检查取消，进入不可取消的 `committing` 阶段。
4. **同一个 SQLite 事务**插入全部新文件夹、录音和提交标记；中途失败全部回滚。不使用冲突覆盖插入。
5. 提交成功后保留成功结果；后续桥接/暂存清理失败只增加 `cleanupPending`，不回滚已提交音频。
6. 正常收尾先等待原生运输和服务结束，再在租约内清理 journal；最后释放保护。启动屏障也先排空/释放原生任务，再执行导入恢复，之后才允许录音恢复、自动清理和普通写入。

恢复逐份读取有界 journal，只接受合法 UUID 和白名单 basename，目标目录由当前应用根目录推导，不信任日志中的任意绝对路径。**数据库提交标记是唯一提交权威**：无标记则清理本任务新文件；有标记则保留最终音频，仅清理暂存/journal。即使 journal 自称 `COMMITTED`，无数据库标记也不能视为成功。

清理前检查专属目录所有条目的归属，不跟随链接，不递归删除未知内容。异常文件、不可读日志或删除失败会保留记录并报告，启动屏障失败后不放行业务写入，可重试。部分文件已经删除时重试幂等。先删除 journal，后删除数据库标记，避免清理中断时将已提交文件误判为未提交；如果进程恰好在两者之间结束，可能留一个无 journal 的提交标记，不会误删音频。无新增音频时清理本任务空目录。
