# BKP-02：任务协调与数据保护

实现日期：2026-10-15。状态：实现及自动化验证已交付，原生时序真机验收待连接设备，工作项保留“进行中”。

对应 [七步计划](manual-backup-and-restore-implementation-plan.md)第二步。完整导入导出、持久化任务日志和后台工作服务仍属后续步骤，本步不开放备份 UI。

## 1. 任务入口与租约

新增 [LibraryCoordinator](../../lib/backup/library_coordinator.dart)，不绑定页面生命周期，提供任务 ID、类型、阶段进度、取消请求、结果及错误状态。

应用使用已绑定库的 `RecordingService.runBackup` 进入任务。先完成启动恢复屏障，再拒绝其他任务或已接受的写入；预约单任务位置后查询原生状态。预约期间立即禁止新写入，不能先检查空闲再加锁。原生状态查询最多等待 10 秒，查询失败保持拒绝；检查期间取消可以直接撤销预约，迟到的只读回复不能执行任务。

执行回调获得当前 `BackupLease`。普通写入方法始终受门禁保护；备份自己的快照/事务接口需要有效租约，拒绝其他库或过期租约。任务结束前等待已授权 IO 结束，再解除保护；授权 IO 失败不能被误报为任务成功。

取消为协作式请求，工作回调通过 `checkCancelled` 在安全边界停止。提交阶段不接受取消；完整文件操作中的取消和回滚由第四/五步实现，不能中途强行解锁仍在写文件的工作。

## 2. 数据写入与一致快照

[RecordingStore](../../lib/storage/recording_store.dart) 的普通录音/文件夹写入入口统一调用 `mutate`。它在首次 await 前占用写入位置，完成或失败后释放。已有写入未结束时备份明确拒绝，让调用方稍后重试，不排一个可能死锁的长数据库事务。

保护范围包括创建/排序/重命名/删除文件夹，保存、移动、重命名、批量更新、软删除、恢复及永久删除录音。业务只读和主题、语言、默认格式设置不被保护锁禁止。

多个存储实例按规范化数据库绝对路径共用协调器；Windows 路径大小写归一，弱引用注册表不保活已关闭的库。显式注入的启动恢复协调器必须与已注册实例一致，不能替换正在使用的门禁。它是单个 Dart isolate 内的协调，不是操作系统文件锁；第三步的工作执行器必须把存储写入转回同一权威接口，不能另起 isolate/engine 后绕过门禁独立打开 SQLite。

`snapshotForBackup` 在短事务中读取：

- 正常录音，不含最近删除。
- 全部文件夹及保存顺序，包括空文件夹。
- 全部本地录音 ID，包括软删除及尚未清理的过期记录，供导入查重。

返回列表/集合不可修改。`backupTransaction` 为后续导入提供租约授权的短事务，不对普通调用方开放“全局解锁”开关。文件准备与数据库提交的一致性仍需第五步的持久化提交记录。

## 3. 保存回调、恢复与清理

`deferMutation` 在保护期间保留 Future，结束后重新检查当前租约再进入写入；紧接着开始另一个任务时继续等待，不在旧任务释放后无条件穿透新锁。

- `RecordingSaveCoordinator` 延后实际入库及原生确认；重复 fileReady 共用同一在途操作，未入库前不 acknowledge，也不因暂时忙碌而丢弃 READY 草稿。
- 保存操作的写入占用覆盖索引提交到原生确认完成，确认未返回时备份不能进入。真实入库失败仍按既有协议 defer，保留重试能力。
- 原生 `recoverRecordings` 及主界面整个恢复/入库流程延后，避免先修改恢复文件再等数据库。
- `purgeExpiredRecordings` 的读取与实际删除作为整体延后，最近删除页、启动和回前台的清理入口自动受保护。
- 主界面录音开始从请求权限前到发出启动命令完成都占用写入位置，覆盖权限授权后的延迟开始。

初始化屏障支持注入未完成备份任务的恢复动作，先完成后允许普通写入、录音恢复或新备份；失败不当作恢复成功，后续可重试。当前没有持久化备份任务，生产默认恢复动作为空；第五步必须接入真实任务日志与同事务提交标记，不能据此声称已支持进程终止后的导入回滚。

## 4. 原生启动与写入者边界

仅依赖 Dart 的 start Future 不够：Android 启动服务调用返回后，实际录音命令还在串行工作队列中。

新增 [RecordingStartReservations](../../android/app/src/main/kotlin/io/github/renial/ya_recorder/RecordingStartReservations.kt)：桥在发送启动 Intent 前创建 token；发送失败撤销；服务在启动处理完成后撤销。服务销毁跳过排队命令时只清理该服务实例已接收的 token，不能误清新实例的请求。查询状态时，尚有排队启动会将旧 idle/failed 映射为带格式的 preparing。

`RecordingSaveProtocol` 另提供非阻塞写入租约摘要，状态返回附带 `backupBlocked`。未确认静止或超时写入者的租约即使留在进程内，也会阻止备份；不能只因界面已经显示 idle 就进入。读取摘要不获取媒体校验的长锁，避免在 Android 主线程等待整段验证。

原生服务通过实例所属标记更新共享状态，销毁中的旧实例不能把新实例的状态重置为 idle。现有事件字段和录音控制命令保持兼容，Dart 对未携带 `backupBlocked` 的旧状态默认 false；正式备份必须使用匹配的新原生构建。

## 5. 界面边界

主界面观察保护状态，禁用录音入口，解除保护后刷新列表；页面销毁移除监听，不取消仍在处理的保存。其他管理页即使仍有可点击入口，其真实存储写入也会被拒绝。全部页面的专用禁用文案、任务入口和通知导航在第六步实现。

本步没有后台服务、URI 操作和任务持久化，不能承诺锁屏后任务持续执行或进程重启恢复；这些分别属于第三步及第五步。

## 6. 验证与剩余真机清单

自动化覆盖任务预约、并发写入、暂停等原生状态、状态查询取消、失效租约、授权 IO 排空、事务失败、快照及软删除 ID、偏好可写、自动清理延后、重复 fileReady、确认等待和权限弹窗竞态。结果及产物见 [验证快照](../verification/bkp02-coordination-2026-10-15.json)。

ADB 检查无连接设备，未安装 APK 或录制音频；原生真实生命周期仍需验证：

1. 用户拒绝/延迟授权、开始录音、暂停、停止入库和取消期间不能进入备份任务。
2. 服务已收到启动 Intent、工作线程尚未执行时，状态查询显示 preparing；Activity 重建仍保持保护。
3. 销毁/重新创建服务时，旧实例清理不会覆盖新实例状态；失败发送及跳过排队命令正确释放自己的预约。
4. 录音停止/确认与回前台恢复、过期清理交错时没有提前入库、误删或丢失 READY 草稿。
5. 写入者不能确认静止时备份拒绝进入，不改动残留文件。

真机验收留在 BKP-02 备注中；只有设备验证待完成时，可继续推进依赖其已实现接口的 BKP-03，不重复本轮已通过检查。
